ТЕХНИЧЕСКОЕ ЗАДАНИЕ

«Разработка сервиса для автоматического учёта и
оценки продуктовых решений команд»

Краткое техническое задание
Разработать веб–сервис для автоматического учёта и оценки продуктовых решений команд
на хакатонах и конкурсах. Сервис принимает заявки команд (репозиторий с кодом,
документацию, презентацию, скринкаст), выполняет автоматические проверки (статический
анализ кода, валидация структуры документации и слайдов презентации, наличие и анализ
скринкаста), формирует сводный балл по настраиваемым критериям и предоставляет жюри
панель ручной экспертной оценки. Дополнительно: модуль автоматической проверки
алгоритмических задач (sandbox-исполнение, тесты, лимиты по времени и памяти). Стек – на
усмотрение команды.
Полное техническое задание
Основная задача состоит в том, чтобы разработать MVP веб-сервиса для автоматического
учёта и оценки продуктовых решений команд хакатона, обеспечивающего приём заявок,
автоматические формальные проверки артефактов, экспертную оценку жюри и
формирование итогового рейтинга команд.
На хакатонах и конкурсах по продуктовому программированию жюри обрабатывает большое
количество однотипных артефактов: репозитории с кодом, документацию, презентации,
видеодемонстрации. Ручная проверка занимает значительное время, критерии оценки
применяются неоднородно, а часть формальных требований (наличие README, структура
слайдов, присутствие скринкаста) проверяется вручную. Это снижает прозрачность оценки и
нагружает экспертов.
Командам предлагается разработать веб-сервис, который автоматизирует приём,
формальную проверку и предварительную оценку продуктовых решений
команд–участников, оставляя жюри только содержательную экспертную часть работы.
Пользователями сервиса будут:
 Участники команд – загружают артефакты решения, отслеживают статус проверок и
обратную связь.
 Жюри/эксперты – просматривают результаты автопроверок, ставят оценки по критериям,
оставляют комментарии.
 Организаторы – управляют этапами конкурса, настраивают критерии и веса, формируют
итоговую таблицу результатов.
Функциональные требования к MVP (прототипу)
1. Учёт команд и заявок:
 Регистрация и аутентификация пользователей с ролями: участник, член жюри,
организатор.
 Создание команд, добавление участников, привязка к кейсу хакатона.
 Личный кабинет команды с возможностью загрузки и обновления артефактов решения.
2. Проверка кода решения (основная функция):
 Приём ссылки на репозиторий (Git) или загрузка архива проекта.
 Автоматический статический анализ: линтеры, базовые метрики (LOC, цикломатическая
сложность), детекция секретов в коде.
 Проверка структуры репозитория: наличие README, лицензии, файла зависимостей,
инструкции по запуску.
 Опциональный запуск тестов команды в sandbox-окружении (Docker) с фиксированными
лимитами.

3. Проверка сопроводительной документации:
 Загрузка документации в формате PDF, DOCX или Markdown.
 Валидация наличия обязательных разделов: описание работы системы, инструкция по
развёртыванию, инструкция по эксплуатации.
 Проверка минимального объёма и базовая оценка качества (длина разделов, наличие
изображений/схем, дополнительные документы).
4. Проверка презентации для demo day:
 Загрузка презентации в формате PPTX или PDF.
 Проверка фактического наличия презентации и подсчёт количества слайдов.
 Валидация соответствия структуре: проблема, решение, целевая аудитория,
технологический стек, демо, команда, контакты – список настраивается организатором.
5. Проверка скринкаста решения:
 Загрузка видеофайла или ссылки на видеохостинг.
 Проверка фактического наличия скринкаста, длительности и базовых технических
параметров (разрешение, кодек).
 Извлечение аудиодорожки и автоматическая транскрипция; генерация краткого
текстового описания скринкаста (саммари) для проверяющих.
6. Оценка и рейтинг:
 Настраиваемые критерии оценки и их веса со стороны организатора.
 Расчёт суммарного балла команды как взвешенной суммы автоматических и экспертных
оценок.
 Панель жюри со списком команд, артефактами, результатами автопроверок и формой
выставления экспертных оценок и комментариев.
 Публичная (или внутренняя) таблица результатов с сортировкой команд по итоговому
баллу.
Дополнительная задача – модуль алгоритмических проверок
Отдельный модуль для проверки алгоритмических решений по аналогии с олимпиадными
системами:
 Загрузка задачи организатором: условие, набор тестов (входы и ожидаемые выходы),
лимиты по времени и памяти.
 Отправка участником решения на одном из поддерживаемых языков (минимум один –
Python, C++ или Java).
 Запуск решения в изолированном sandbox с контролем времени и памяти, сравнение
вывода с эталоном.
 Вердикты: OK, WA, TL, ML, RE, CE; история попыток и баллы по задачам.
Технические и нефункциональные требования
 Архитектура: веб-сервис с REST или GraphQL API и веб-клиентом; возможно
разделение на frontend и backend.
 Технологический стек – на усмотрение команды; приветствуются современные
production-готовые решения.
 Контейнеризация (Docker) и инструкция по развёртыванию решения одной командой
(например, docker compose up).
 Хранение данных – реляционная СУБД (PostgreSQL/MySQL) или альтернатива с
обоснованием.
 Длительные задачи (анализ кода, обработка видео, sandbox-проверки) выполняются
асинхронно в очереди задач.
 Соблюдение базовых требований к безопасности: хеширование паролей, разделение
прав по ролям, защита от загрузки исполняемых файлов в обход sandbox.
 Адаптивный веб-интерфейс с поддержкой современных браузеров.
Результаты работы и состав сдачи

1. Репозиторий с исходным кодом проекта в публичном или приватном Git с
предоставленным доступом.
2. Сопроводительная документация: описание архитектуры, инструкция по
развёртыванию, инструкция по эксплуатации, дополнительные документы (тестовые
данные, скриншоты интерфейса).
3. Презентация проекта для demo-day – PPTX или PDF, объёмом 8 – 15 слайдов.
4. Скринкаст с демонстрацией работы решения длительностью 3 – 5 минут.
5. Развёрнутый стенд (локально на защите или публично доступный URL) с
предзагруженными демо-данными.
Сроки и этапы
 Дни 1 – 2: проектирование архитектуры, разработка модели данных, базового API и
каркаса интерфейса.
 Дни 3 – 4: реализация основных проверок (код, документация, презентация, скринкаст) и
панели жюри.
 День 5: интеграция модулей, оценка и рейтинг, тестирование, доработки, подготовка
скринкаста и презентации.
 День 6: очная защита проекта перед жюри – демонстрация решения, ответы на вопросы,
обсуждение результатов.
Ограничения
 Срок разработки – до 06.06.2026; защита проводится 06.06.2026 очно.
 Использование сторонних AI-сервисов и open-source библиотек допускается при условии
указания источников в документации.
 Запрещены готовые коммерческие платформы автоматической оценки в качестве основы
решения.
